atom 06 · hardware

INSIDE THE CPU

ALU
Arithmetic Logic Unit — performs +, −, ×, ÷ and comparisons (>, ==…). Every C arithmetic expression ends up here.
CONTROL UNIT
CU — fetches instructions from memory, decodes them, and commands the other units. The orchestra conductor.
REGISTERS
Tiny, ultra-fast cells inside the CPU holding values being worked on right now — the machine's scratchpad.
CLOCK
Synchronizes everything; its speed (GHz = billions of ticks/second) bounds how fast instructions complete.
FETCH–DECODE–EXECUTE
The eternal cycle: fetch next instruction from memory → decode what it means → execute it → repeat. Billions of times per second.
machine-cycle.c — as the CPU sees it
while (power_on) {
    instruction = fetch(PC);   // program counter
    meaning     = decode(instruction);
    execute(meaning);         // ALU or memory
    PC = PC + 1;               // next instruction
}
/* a running C program is this loop,
   unrolled into billions of cycles */
WHY YOU CARE
Every statement you write in C is ultimately a short sequence of these machine cycles. Simpler expressions = fewer cycles = faster programs.

atom 18 · algorithms

ALGORITHM — DEFINITION

DEFINITION
An algorithm is a finite, ordered, unambiguous sequence of elementary steps that transforms given inputs into the required outputs and halts.

Five properties — each is a veto:

1 · Input
Zero or more quantities supplied beforehand.
2 · Output
At least one result — no output, no problem solved.
3 · Definiteness
Every step is exact — "add 5 to x", never "improve x".
4 · Finiteness
Terminates after a finite number of steps. Loop forever = not an algorithm.
5 · Effectiveness
Each step basic enough to be performed exactly and in finite time.
RECIPE ANALOGY
Ingredients = input, the dish = output, numbered steps = the algorithm. A recipe missing baking time (finiteness) or saying "cook until it seems right" (definiteness) fails the same tests.
algorithm vs program
/* ALGORITHM — language-free */
max ← a
if b > max then max ← b

/* PROGRAM — algorithm + syntax
   + types + I/O machinery        */
if (b > max) max = b;

// one algorithm, infinitely many
// programs (C, Python, Java…)

atom 22 · structure

THE STRUCTURED THEOREM

BÖHM & JACOPINI, 1966
Any computable algorithm can be expressed using only three control structures — sequence, selection, and repetition. No goto needed. Ever.
SEQUENCE
A then B then C — one entry, one exit.
SELECTION
if-then-else — choose one of two paths.
REPETITION
while — repeat while a condition holds.
SINGLE ENTRY, SINGLE EXIT
Each block is a black box: one way in, one way out. Nest black boxes freely — the whole program stays a single straight line of black boxes. That's what makes it provable and readable.
spaghetti vs structured
/* SPAGHETTI ✗ — flow jumps anywhere */
   goto retry;
   ...
retry:
   scanf("%d", &x);

/* STRUCTURED ✓ — shape of the code
      is the shape of the logic     */
   do {
       scanf("%d", &x);
   } while (x < 0);

/* "goto considered harmful"
   — Dijkstra, 1968 */
C EMBODIES THE THEOREM
C's if/else, while, for, do-while are factory-made building blocks of the three structures — modules M2 and M3 cover them atom by atom.

  • Level 0 — state the whole problem in one sentence: "process the payroll for a department."

SHORT-CIRCUIT EVALUATION

THE RULE
&& stops at the first false — the whole thing is false, why continue? || stops at the first true — already true, why continue?
short-circuit.c
(x != 0) && (y / x > 2)
/* x == 0?  first part false →
   y/x NEVER EVALUATED →
   no division by zero!   */

(count > 0) || (total / count > 5)
/* count > 0? → true already,
   division never runs     */
⚠ ORDER IS A SAFETY FEATURE
Swap the operands — (y/x > 2) && (x != 0) — and the division crashes first. The guard must come before the guarded.

             then do the work  */

    result = value / divisor;

   index < size && arr[index] == key

SIDE-EFFECTS ARE SKIPPED TOO
0 && (i++) — the i++ never runs. If an operand has a side effect, short-circuiting decides whether it happens. Keep side effects out of conditions.
WHY C DOES THIS
Speed (skip needless work) and safety (guard idiom). It's a language feature with exactly one rule — learn it once, use it forever.

/* how many passes? unknown —
   no for-header could say it  */
NEVER DO THIS
Don't modify i inside a for body — the header owns it. One update per pass, done by ④. Double-updating is the fast lane to skipping values.
STYLE POINT
Mixing them arbitrarily is worse than either alone — consistency lets readers predict your loops' shapes.

All of these are legal. The header's job is to let a reader see the loop's whole trajectory at a glance — a header that hides the update invites bugs.

Loop-control var unsigned? i >= 0 is always true — 0−1 wraps to a huge number. Classic infinite loop.

CONDITIONAL LOOPS — THE FOUR KINDS

THE PROBLEM
Counting loops know their pass count up front. Real data doesn't: "read scores until the user says stop" — the loop condition is data-driven. Four idioms cover every case.
82 · SENTINEL
loop until a special end-marker value arrives (-1)
84 · END-OF-FILE
loop while scanf successfully reads items
85 · FLAG
loop until a 0/1 event flag gets set
86 · VALIDATION
re-ask until input is in the legal range
the shared skeleton
scanf("...", &item);     /* PRIME */
while (item-is-not-the-end) {
    process(item);            /* work    */
    scanf("...", &item);   /* NEXT    */
}
/* one read BEFORE, one read
   INSIDE — the priming-read
   pattern, next atom       */
HOW TO CHOOSE
Is there a value that can't be data? → sentinel. Is input from a file/redirect? → EOF. Searching for an event? → flag. Bad user input? → validation.

THE SENTINEL LOOP

scores.c
#define SENTINEL -1

sum = 0;  count = 0;
printf("score (-1 ends)> ");
scanf("%d", &score);          /* PRIME  */

while (score != SENTINEL) {
    sum   = sum + score;
    count = count + 1;
    scanf("%d", &score);      /* NEXT   */
}
avg = (double)sum / count;
SENTINEL CHOICE RULES
Must be impossible as real data (−1 for scores, 0 for a product ID, EOF for files) — and prominently documented in the prompt.
$ ./scores
score (-1 ends)> 80
score (-1 ends)> 90
score (-1 ends)> 70
score (-1 ends)> -1
Average = 80.00
/* 3 values entered; -1 itself
   is NEVER processed — it only
   ends the loop            */
⚠ SENTINEL ≠ DATA
If −1 is a legal score, the loop eats it and stops early. Choose a sentinel outside the data's domain — that's the entire design decision.
WHY -1 GETS SKIPPED
The test != SENTINEL runs before the body — when −1 arrives, the condition is false and the body never sees it. Pre-test design pays off.

DEFINITION
A priming read fetches the first value before the loop so the first test has something to test; a get-next read at the end of the body fetches each subsequent value. Two reads. Both. Always.

the two failure modes
/* ✗ missing PRIME:
   tests garbage on pass 1   */
while (score != -1) {
    scanf("%d", &score);

}

   same value forever,
   infinite loop         */

    sum += score;      /* score never changes */

WHY THE ORDER MATTERS
Process then read: the body works only on values that passed the test. Read-then-process lets the sentinel leak into the sum — a wrong-answer bug, not a crash.

THE END-OF-FILE LOOP

THE SECRET OF scanf
scanf returns the count of items read — 1 on success, 0 on mismatch, EOF (−1) when input ends. That return value is the loop condition.
eof.c
count = 0;  sum = 0;

while (scanf("%d", &x) == 1) {
    sum   += x;
    count += 1;
}
printf("avg = %.2f\n",
       (double)sum / count);

/* textbook form:
   while (scanf(...) != EOF)  */
PRIMING READ FOR FREE
The scanf is the test — value read and condition checked in one expression. No separate priming read needed; that's the elegance.
$ ./eof < data.txt
avg = 78.33
/* input redirected from a file:
   70 80 85 — file end triggers
   scanf to return EOF and the
   loop exits cleanly        */

/* Ctrl-Z (Windows) = EOF      */

A special constant from stdio.h meaning "no more input". It's a status, not a character — it can't be typed, only triggered by file-end or the Ctrl-D signal.
⚠ == 1 IS SAFER THAN != EOF
Typed letters instead of numbers? scanf returns 0 — != EOF loops forever on the bad input. == 1 stops on any failure, not just end-of-file.

THE FLAG LOOP

DEFINITION
A flag is an int variable acting as an event signal: 0 = not yet, 1 = it happened. The loop runs while (!flag) — until the event flips it.
search.c — find key in array
found = 0;                    /* flag down  */
i = 0;

while (!found && i < SIZE) {
    if (a[i] == key)
        found = 1;            /* flag UP    */
    else
        i = i + 1;
}
if (found)
    printf("at index %d\n", i);
else
    printf("absent\n");

⚠ THE DOUBLE CONDITION
!found && i < SIZE — order is load-bearing: stop searching either because we found it or ran out of data. Drop the i < SIZE guard and you read past the array (crash/garbage).
WHY NOT break?
break inside the if is shorter — but the flag version keeps single-exit structure (atom 22) and works identically in pseudocode. Learn the flag; use break knowingly.
FLAG NAMES
found · done · error · sorted · changed — past-tense/adjective names that read as conditions.

THE INPUT-VALIDATION LOOP

printf("rate (0-10)> ");
scanf("%lf", &rate);

while (rate < 0.0 || rate > 10.0) {
    printf("Invalid! (0-10)> ");
    scanf("%lf", &rate);
}
/* rate is now guaranteed legal */
do-while-version — same job, cleaner
do {
    printf("rate (0-10)> ");
    scanf("%lf", &rate);
} while (rate < 0.0 || rate > 10.0);

note the do-while version has no duplicated prompt — the body must run once, and it says so structurally.

$ ./validate
rate (0-10)> 15

Invalid! (0-10)> 7.5
accepted → program continues
THE DESIGN INSIGHT
Validation is the one place where "at least once" is inherent — you must ask before you can test the answer. This is exactly the shape do-while was born for.
⚠ VALIDATE AT THE BOUNDARY
Guard every value at input time, not later at use time — garbage that enters the program spreads and multiplies.

LOOP DESIGN — THE 3 QUESTIONS

Answer these before
writing the loop —
and any loop is correct.

Q1 · Initialize
What are the control variable and every accumulator set to, before the first test? (identities! sum→0, product→1)
Q2 · Condition
What exactly continues the loop? When does it stop? What is true at exit — i = n+1? found? EOF?
Q3 · Update
What changes each pass so the loop provably approaches termination?
+ Body placement
What repeats — and what must stay outside (run once, not n times)?
design-sheet — sum 1..n
GOAL : sum = 1+2+…+n

Q1 : sum = 0,  i = 1        ✓
Q2 : continue while i ≤ n
     exit when   i == n+1   ✓
Q3 : i = i + 1  (approaches n)   ✓
BODY: sum = sum + i  — nothing
      else belongs inside    ✓

CODE:
sum = 0;
for (i = 1; i <= n; i++)
    sum += i;       /* 6 lines → 2 */
⚠ MOST COMMON DESIGN BUG
An initialization inside the body: while(...){ sum=0; sum+=i; ... } — the accumulator resets every pass, and the final sum is just the last value.

for (row = 1; row <= 3; row++) {    /* OUTER  */

ATOM: do-while

do { body; } while (condition);
SEMANTICS — POST-TEST
Body first, test after: ① run the body ② evaluate condition ③ nonzero → repeat. The body runs at least once — even if the condition is false from the very start.

do {
    printf("1-add 2-del 0-quit> ");
    scanf("%d", &choice);
    run(choice);
} while (choice != 0);

   before there's anything
   to test — inherent shape  */

} while (c) without ; — syntax error, and the compiler's message points at the next line, misdirecting you. The only loop that ends in ;.

↓
② condition ?
true ↺ repeat   ·   false → exit
